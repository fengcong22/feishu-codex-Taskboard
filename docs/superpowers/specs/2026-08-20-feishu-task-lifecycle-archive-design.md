# 飞书待剪辑任务生命周期归档设计

日期：2026-08-20

## 背景

当前 Bridge 在飞书记录从其他状态进入 `待剪辑` 时创建 Taskboard 手动任务。任务创建后位于 Taskboard 的“等待认领”列（Taskboard 状态 `todo`）。用户接单并启动 Codex 后，Taskboard 自己负责把任务推进到“处理中”等执行状态；Bridge 不应根据飞书字段变化擅自覆盖这些执行状态。

本次只补充“离开待剪辑时清理等待认领任务”的生命周期行为，不提前设计飞书字段到 Taskboard 各列的通用映射。

## 目标与非目标

### 目标

1. 记录从 `待剪辑` 变为其他值时，找到该记录对应的、仍处于 Taskboard `todo` 状态的飞书剪辑任务。
2. 将这些未认领任务归档，使其从“等待认领”列消失，同时保留历史记录。
3. 归档操作可重放、可恢复：Taskboard 暂不可用时进入现有有限重试；Bridge 在归档成功但状态提交前崩溃时，重放不会重复产生副作用。
4. 已经进入 `in_progress`、`in_review`、`done` 或其他非 `todo` 状态的任务不被自动归档或中止。

### 非目标

- 不把飞书字段状态映射到 Taskboard 的“处理中”“等你确认”等列。
- 不自动启动、停止或取消 Codex。
- 不删除 Taskboard 任务；归档任务仍可在 Taskboard 的归档区域查看和恢复。
- 不改变“每次重新进入 `待剪辑` 可以产生新的事件和任务”的现有语义。
- 不归档其他字段、其他表或其他记录对应的任务。

### 已知并发边界

离开事件可能在飞书/SDK 或 Bridge 重试队列中延迟。如果同一记录在旧离开事件真正执行前已经快速完成“离开待剪辑 → 再次进入待剪辑”，按当前“同一记录的全部匹配 `todo` 任务”规则，旧事件可能把新一轮任务一并归档。当前先接受此边界；如未来需要严格按轮次隔离，应增加记录版本或事件顺序约束。

## 触发规则

在已配置表的触发字段上：

| 变化 | Bridge 行为 |
| --- | --- |
| 其他值 → `待剪辑` | 维持现有逻辑，创建 `todo` 任务 |
| `待剪辑` → 其他值 | 执行归档效果，只处理匹配记录的 `todo` 任务 |
| `待剪辑` → `待剪辑` | 忽略，不归档、不创建 |
| 其他值 → 其他值 | 忽略 |
| 非触发字段变化 | 忽略 |

判断前后值时继续使用现有的显示值标准化和字段配置；不能把单元格内容解释为路径、命令或 prompt。

## 任务匹配边界

Taskboard 任务描述中的服务端元数据扩展为可复用的“流程身份”字段。归档候选必须同时满足：

- `source = feishu-base`；
- `baseToken`、`tableId`、`recordId` 相同；
- 触发字段身份相同：优先比较 `triggerFieldId`，缺失时回退比较 `triggerField`；
- `triggerValue` 相同；
- 任务当前未归档且 Taskboard 状态为 `todo`。

不以任务标题、项目包别名或事件 ID 单独匹配。这样同一条记录多次进入 `待剪辑` 产生的多个未认领任务都会被清理，同时不会误伤未来其他字段流程或已经开始执行的任务。现有旧元数据没有 `triggerFieldId` 时，使用字段名回退兼容。

## 处理流程

1. `decideRecordChange` 将“离开触发值”识别为一个带有归档效果的 ignored 决策；普通 ignored 事件仍完全不访问 Taskboard。
2. Bridge 领取并持有事件租约后，调用 Taskboard 列表接口读取活动任务，解析服务端元数据并筛选匹配候选。
3. 逐个归档候选，使用 Taskboard 返回的 `version` 做乐观并发控制。
4. 若任务在列表和归档之间被用户/Codex 推进到非 `todo`，重新读取该任务并跳过，不覆盖执行状态。
5. 归档接口返回成功、任务已归档或没有候选时，持久化为成功的 ignored 结果（原因例如 `left_trigger_archived`）。
6. 网络、HTTP 429/5xx 等临时错误沿用现有 `retry_wait`、有限退避和 `dead_letter` 机制。部分候选已归档后重试只会看到剩余活动候选，因此操作保持幂等。

## Taskboard 客户端边界

复用现有 Taskboard API：

- `GET /api/tasks?archived=false` 获取活动任务；
- `GET /api/tasks/:id` 在乐观版本冲突时重新确认状态；
- `POST /api/tasks/:id/archive` 携带当前 `version` 归档。

客户端校验成功响应结构，并将异常转换为安全错误码。Taskboard 现有归档接口不需要改造。

## 持久化与可靠性

- 离开事件仍按 `event_id` 写入现有状态机，正常重放不会重复归档已归档任务。
- 归档成功后、Bridge 提交 `succeeded` 前崩溃时，重启补偿会再次筛选活动 `todo` 候选；已归档任务不会再次出现。
- 租约失效、状态锁超时和 Taskboard 临时不可用继续使用现有 fencing、heartbeat 和有限补偿机制。
- 不能宣称跨 Taskboard 外部副作用与状态提交崩溃窗口的绝对 exactly-once；目标仍是 at-least-once 加可重放归档。

## 测试与验收

### 单元/集成测试

- 决策层正确区分进入、离开、保持和普通变化。
- 离开事件只筛选同 Base、表、记录和触发流程的 `todo` 任务。
- 多个历史未认领任务全部归档；非 `todo` 任务保持不变。
- 版本冲突后重新读取，任务已进入执行态时跳过；仍为 `todo` 时使用新版本重试。
- Taskboard 暂不可用进入 `retry_wait`，恢复后最终归档。
- 归档成功后的事件重放不重复归档或创建任务。
- 现有进入 `待剪辑`、事件去重、Taskboard 创建和可靠性测试保持通过。

### 手工验收

1. 使用测试表记录从其他状态改为 `待剪辑`，确认出现一条“等待认领”任务。
2. 不接单，改回其他状态，确认该任务从“等待认领”消失，并可在归档任务中查到。
3. 再次改为 `待剪辑`，确认可以创建新的等待认领任务。
4. 对另一条任务先点击启动 Codex，再改变飞书状态，确认任务仍由 Taskboard 保持在执行状态，不被 Bridge 归档。
