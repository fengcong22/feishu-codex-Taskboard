# 飞书多 Base / 学科 Auto-Cut 与上传工作流设计

日期：2026-08-21

状态：已实现；以下三阶段修订覆盖原始单触发值设计中与其冲突的描述

## 三阶段修订（2026-09-09）

实现保留旧版 `tables` 的单可开始值流程，同时把 Taskboard 管理的 subject 扩展为 `initial`、`first_review`、`final_review` 三个固定阶段。每个阶段独立保存启用状态和同一状态字段下的单选 option；只有从其他 option 进入已启用阶段 option 才登记该阶段任务，离开或跨阶段时只归档上一阶段仍为 `todo` 的任务。它不是“飞书状态直接映射 Taskboard 列”：`in_progress`、`in_review`、`done` 等执行状态仍由 Taskboard/Codex 管理。

自动执行由 Taskboard 发起，Bridge 永不启动 Codex。只有专用接口登记的真实事件任务、可验证的活动配置版本为 `automatic`、项目包处于本机启用白名单且 `CODEX_TASKBOARD_ALLOW_AUTOMATIC_EXECUTION` 显式开启时，Taskboard 才可自动调度。模拟事件、旧版登记体、普通任务、复制的描述标记或标签均不得取得自动执行资格。本文后续出现“每个学科只有一个可开始值”“第一期仅手动”等原始阶段性表述时，以本修订和根目录 `AGENTS.md` 为准。

## 1. 背景

当前仓库中的 Bridge 已经能够通过飞书官方 SDK 长连接接收多维表格记录变化，按 Base、子表、字段、触发值和受控项目包别名筛选事件，并在 Taskboard 创建或归档受控的手动任务。当前 Bridge 不自动启动 Codex，Taskboard 的 `start-ai` 仅支持现有的手动启动流程，Auto-Cut 生成的剪映草稿 ZIP 和后续上传尚未纳入统一任务生命周期。

用户需要把多个飞书 Base、每个 Base 中选定的学科子表、不同的可开始字段值、Auto-Cut 包、剪辑产物和上传目标组织成一个可配置的本机工作流。不同 Base 之间的信息必须隔离；同一 Base 中未选择的子表不应显示或监听；配置只有显式启用后才接收任务。

本设计覆盖以下目标：

- Taskboard 通过粘贴 Base 链接读取 Base、子表和字段元数据；
- Base 下显示用户选中的学科子表，名称与飞书保持一致；
- 每个学科子表独立保存触发字段、唯一可开始值、执行模式、Auto-Cut 包、并发和上传配置；
- 配置先保存为草稿，点击“启用”后才加入 Bridge 监听白名单；
- 手动启动、拖拽到“处理中”和自动模式使用同一个幂等 Auto-Cut 执行入口；
- 手动模式支持“待验收”，自动模式跳过“待验收”；
- 剪辑状态与上传状态独立；
- 初期允许手动选择 ZIP，Taskboard 自己计算并记录 SHA-256；
- 后续支持按学科修改 ZIP 获取路径以及本地/NAS 上传目标；
- 共享配置可以在另一台电脑导入，但不携带本机路径、凭据、运行状态和历史任务。

## 2. 已确认的产品决策

### 2.1 Base 与学科身份

每个学科子表的稳定身份是：

```text
subjectKey = baseToken + ":" + tableId
```

`baseToken` 和 `tableId` 是机器身份；Base 名称、子表名称和字段名称只是显示文本。名称变化通过元数据刷新更新显示，不改变历史任务身份。

多个 Base 完全隔离。Taskboard 不把不同 Base 的子表合并成一个业务表，也不使用名称作为跨 Base 的匹配键。

### 2.2 显示与启用

“显示在 Taskboard”与“启用 Bridge 接收”是两个独立开关：

- 显示但未启用：可以在 Base/学科导航中查看和编辑草稿，但不会接收事件；
- 启用但未显示：可以接收事件，但不出现在导航列表中；
- 新增或修改配置首先保存为草稿；
- 只有点击“启用”并通过本机校验后，配置才进入活动监听白名单；
- 停用子表不会自动中止已进入 `in_progress`、`in_review`、`done` 或其他非 `todo` 状态的任务。

### 2.3 触发字段与可开始值

每个学科子表只有一个可开始值，但字段名称和值不固定。配置使用真实 `fieldId`，同时保存从飞书读取的 `fieldName` 作为显示文本。可开始值可以来自单选字段的真实选项，也可以是经用户确认的文本值；不会启用通用的“所有状态值映射”。

Bridge 仍遵守现有生命周期不变量：只有从其他值变化到配置的可开始值才创建任务；从可开始值离开时只归档同一 Base、子表、记录和触发字段流程下仍为 Taskboard `todo` 的任务。

### 2.4 Auto-Cut 路由与并发

第一期每个学科绑定一个固定 Auto-Cut 包。配置预留学科代码和分支映射字段，但第一期不启用动态路由。未来可以采用：

```text
subjectCode -> Auto-cut-copyB
subjectCode -> Auto-cut-小学语文
```

或由一个总包在内部按学科代码分支，而不改变 Taskboard 任务身份。

一个 Auto-Cut 包不是只能同时运行一个任务。每个学科或 Auto-Cut 包配置自己的并发组和最大并发数，默认值为 1。达到上限时进入执行队列，验证资源安全后可以调大到 2 或更高。剪映桌面、浏览器、GPU 等共享资源可以使用独立资源组并设置更低的上限。

### 2.5 剪辑、验收和上传

剪辑状态与上传状态分离。

手动模式：

```text
待处理 -> 处理中 -> 待验收 -> 已完成剪辑
                         └-> 阻塞 / 退回重剪
```

自动模式：

```text
待处理 -> 处理中 -> 已完成剪辑
                         └-> 阻塞 / 失败
```

Taskboard 状态映射为：

- `todo`：待处理；
- `in_progress`：处理中；
- `in_review`：手动模式的待验收；
- `done`：已完成剪辑；
- `blocked`：需要人工动作、产物异常或等待重试；
- `canceled`：用户主动取消，不由 Bridge 因飞书字段变化自动设置。

自动模式不进入 `in_review`。手动模式的 Auto-Cut 和 ZIP 校验成功后进入 `in_review`，验收通过后才进入 `done`；退回重剪时保留验收意见并回到可再次执行的待处理阶段。

上传状态独立为：

```text
未排队 -> 上传队列 -> 上传中 -> 已上传
                         └-> 上传失败 / 待重试
```

手动模式必须通过验收后才能自动加入上传队列。自动模式是否自动入队由上传模式配置决定。

## 3. 方案比较与选型

### 3.1 方案 A：只扩展现有 Bridge 和 Taskboard

优点是初期文件数量少，能够复用现有任务数据库和 Codex runner。缺点是 Base 配置、任务执行、Auto-Cut 产物和上传重试会集中在两个已有服务中，状态边界容易再次耦合；多 Base、并发资源组和上传 Worker 会让现有事件处理器变得难以测试。

### 3.2 方案 B：Bridge + Taskboard + 本机流程编排器/Worker（推荐）

Bridge 继续专注于飞书事件接收、筛选、标准化、去重和任务投递；Taskboard 专注于目录展示、任务状态和用户操作；本机流程编排器负责统一执行入口、并发调度、Auto-Cut 适配和产物校验；上传 Worker 负责 ZIP 入队、复制、校验和重试。组件之间使用本机 loopback API 和持久化任务执行记录通信。

这个方案的边界清晰，能够让手动启动、拖拽启动和自动模式共享相同的幂等入口，也能在未来替换 Auto-Cut 包或上传目标而不改变 Bridge 事件规则。

### 3.3 方案 C：轮询 Taskboard 状态并调用脚本

优点是无需马上扩展 Taskboard 状态转换接口。缺点是有轮询延迟，容易在拖拽竞态、进程崩溃和重复启动时产生不一致；无法可靠表达并发租约和上传幂等，不作为长期方案。

### 3.4 选型结论

采用方案 B。第一期仍可以先实现手动 ZIP 选择和人工验收，逐步启用自动产物发现、自动执行和上传 Worker。任何改变当前“Bridge 不自动启动 Codex”的行为都必须先同步更新根目录 `AGENTS.md`、自动化测试和 README，并完成测试表验收；设计稿本身不改变现行运行规范。

## 4. 目标架构

```text
飞书 Base
  └─ 官方 SDK 长连接
       └─ Bridge
            ├─ 活动子表白名单
            ├─ 字段/可开始值筛选
            ├─ 事件去重与可靠投递
            └─ Taskboard 任务创建/归档

Taskboard
  ├─ Base/学科目录
  ├─ 草稿/启用配置
  ├─ 任务状态和人工验收
  └─ 统一执行请求入口

流程编排器
  ├─ 执行幂等 claim
  ├─ Auto-Cut 包适配器
  ├─ 并发资源组调度
  ├─ 草稿/ZIP 产物校验
  └─ 执行状态恢复

上传 Worker
  ├─ ZIP 获取与 SHA-256
  ├─ 上传队列与并发
  ├─ 本地/NAS 目标适配
  └─ 失败重试和冲突保护
```

所有服务只监听 `127.0.0.1`。飞书凭据只存在于 `.env.local` 或批准的密钥管理中；飞书单元格和事件数据不能提供工作区路径、shell 命令、Codex 参数或 prompt。

## 5. Base 链接导入与配置中心

### 5.1 导入流程

Taskboard 的“新增多维表格”入口接收用户粘贴的 Base 链接。链接解析遵循 Base 资源规则：提取 `/base/{token}` 的 Base token，忽略不能作为 Base 身份的其他链接部分；如果链接来自 Wiki，必须先解析 Wiki 节点确认其对象类型是 bitable，再使用真实 Base token。

Taskboard 不直接持有飞书密钥，而是调用本机 Bridge 的元数据预览接口。Bridge 使用已配置的飞书客户端只读获取：

- Base 名称和 token；
- 数据表名称和 table ID；
- 字段名称、field ID、类型和可选项；
- 可用于显示和配置的元数据版本。

预览不会启用任何子表，也不会加入事件订阅白名单。用户选中需要显示的子表后，Taskboard 为每个子表建立草稿配置。

### 5.2 配置模型

概念模型如下：

```text
BaseConfig
  baseToken
  baseName
  sourceUrlLabel
  metadataRefreshedAt
  subjects[]

SubjectConfig
  subjectKey = baseToken + ":" + tableId
  tableId
  tableName
  displayEnabled
  lifecycle = draft | enabled | disabled
  configVersion
  trigger
  title
  execution
  packageRoute
  upload
```

`trigger`：

```text
{
  fieldId,
  fieldName,
  startValue,
  optionId: optional
}
```

`execution`：

```text
{
  mode: manual | automatic,
  concurrencyGroup,
  maxConcurrent,
  resourceGroups: []
}
```

`packageRoute` 第一期开启固定包：

```text
{
  routeMode: fixed,
  packageAlias,
  subjectCodeFieldId: optional,
  branchMap: optional
}
```

`upload`：

```text
{
  enqueueMode: manual | automatic,
  artifactSourceMode: manual_select | watch_directory | driver_report,
  artifactSourcePath: local-only,
  targetId: optional,
  targetPath: local-only,
  uploadConcurrency: positive integer
}
```

路径字段只存在本机配置中，不由飞书单元格覆盖。共享配置使用路径别名或空绑定状态，不导出绝对路径和凭据。

### 5.3 草稿与启用

修改配置只产生新草稿版本。点击启用时，系统必须验证 Base、子表和 field ID 仍然存在，触发值完整，包别名在本机白名单中，工作区有效，并发数为正整数，路径格式合法。验证失败不会替换当前活动版本。

启用操作要以原子配置快照切换为边界：Bridge 只读取活动版本；正在处理的任务保存创建时的配置快照，不因后续修改而改变执行路径或上传目标。

## 6. 任务创建、执行和并发

### 6.1 Bridge 任务创建

Bridge 对满足触发条件的事件创建 `todo` 任务。任务元数据必须包含：

- `baseToken`、`tableId`、`recordId`；
- 触发字段 ID/名称和可开始值；
- 事件 ID 和任务创建轮次标识；
- 学科配置 ID/版本；
- 固定 Auto-Cut 包别名和包版本引用；
- 标题字段和记录标题；
- 执行模式与上传模式的显示信息。

飞书事件内容只作为标准化上下文，不作为 shell、路径或 prompt。未知或缺失包别名创建阻塞任务，不执行本地操作。

### 6.2 三种启动入口

以下入口都调用同一个 `requestExecution(taskId, trigger)`：

1. 手动模式点击“启动 Auto-Cut”；
2. 用户把任务拖到 `in_progress`；
3. 自动模式的任务创建后由编排器自动进入 `in_progress`。

当前规范禁止 Bridge 自动启动 Codex，因此第 3 项在实现前必须通过规范变更、测试和 README 评审；手动入口可以先单独实现和验证。

`requestExecution` 先检查任务身份、状态、配置快照和当前执行 claim，再将任务放入调度器。已有活动执行、已成功执行或同一请求重放时返回原执行结果，不创建第二个运行实例。

### 6.3 任务状态与执行状态

Taskboard 的任务状态表达用户流程，执行记录表达机器流程。一个 `in_progress` 任务可以有：

```text
executionState = queued | running | blocked | retry_wait | succeeded | failed
```

`queued` 任务是否在处理中列显示为“排队中”徽标，需要在 UI 评审时最终确定；无论采用列内徽标还是独立队列窗口，不能把尚未获得执行租约的任务误报告为 Auto-Cut 已运行。

### 6.4 并发调度

调度器以 `concurrencyGroup` 和资源组租约控制并发：

- 同一任务只能有一个活动执行 claim；
- 每个并发组不超过 `maxConcurrent`；
- 需要共享剪映桌面或浏览器时使用独立资源组；
- 每次执行获得独立的 `executionId` 和隔离工作目录/输出目录；
- 超出上限的任务保留在队列，等待有限退避和租约恢复；
- 上传 Worker 使用独立的上传并发限制，不占用剪辑并发名额。

执行 claim、租约和重试记录必须使用与现有 Bridge 相同的持久化、锁和原子替换原则。系统仍是至少一次语义，不宣称跨外部 Codex/Taskboard 副作用的绝对 exactly-once。

## 7. Auto-Cut 适配器与产物契约

编排器不假设所有 Auto-Cut 包使用相同的脚本或目录结构，而是通过包适配器执行受控工作区 prompt，并将结果标准化为：

```text
ExecutionResult
  executionId
  status = succeeded | blocked | retryable_failure | permanent_failure
  draftPath
  zipPath
  zipSha256
  reportRef
  blockingCode
  blockingMessage
```

第一期可以由 Taskboard 在执行结束后手动选择 ZIP；后续适配器或目录扫描器可以自动填充 `zipPath`。适配器必须区分：

- Auto-Cut 成功但产物缺失；
- 需要用户授权、素材证据或高风险确认；
- 临时网络、进程或资源错误；
- 不可恢复的配置或包错误。

只有可编辑剪映草稿和完整 ZIP 均通过校验，才允许将执行视为成功。不能用一个渲染视频替代可编辑草稿，也不能把阻塞状态标记为完成。

## 8. 验收策略

### 8.1 手动模式

Auto-Cut 和 ZIP 校验成功后，任务进入 `in_review`。验收面板显示草稿路径引用、ZIP 文件、SHA-256、执行日志摘要和产物校验结果。

- 验收通过：`in_review -> done`；
- 退回重剪：保留意见，回到 `todo` 或显式“待重剪”入口；
- 发现系统阻塞：进入 `blocked`，不自动上传。

### 8.2 自动模式

Auto-Cut 和产物校验成功后直接进入 `done`，跳过 `in_review`。上传是否自动入队由 `enqueueMode` 决定。

## 9. ZIP 获取与上传

### 9.1 手动选择

第一期在 `in_review` 或 `done` 任务中提供“选择 ZIP”。系统执行以下检查：

1. 文件存在且扩展名为 `.zip`；
2. 文件在读取期间大小和修改时间稳定；
3. ZIP 中央目录可读取；
4. 条目路径不包含目录穿越或绝对路径；
5. 通过 Auto-Cut 包对应的最小草稿结构校验；
6. 计算 SHA-256 并记录在任务产物中。

系统不要求用户额外生成 `.sha256` 文件，不修改原始 ZIP 和原始剪映草稿。必要时可以把 ZIP 复制到本机受控产物缓存，但不改变用户源文件。

### 9.2 自动扫描

后续可以为学科配置 `watch_directory`，由本机扫描器在绝对路径下按记录 ID、任务 ID 或受控文件名前缀匹配 ZIP。扫描器不能读取飞书单元格中的目录；路径变更只影响后续未绑定产物的任务。

### 9.3 上传流程

上传 Worker 使用临时文件和校验后改名：

1. 以任务和产物 SHA-256 建立幂等键；
2. 在目标目录写入临时文件；
3. 复制完成后计算目标 SHA-256；
4. 校验一致后改为正式文件名；
5. 目标已有相同哈希时直接标记已上传；
6. 目标已有同名不同哈希时默认进入冲突，不覆盖原文件。

本地路径和 Windows UNC/NAS 路径都先使用文件系统适配器。初期 NAS 凭据由操作系统挂载或外部凭据管理提供，不写入共享配置、任务描述或日志。

上传失败只改变 `uploadStatus`，不把已经完成剪辑的任务改回剪辑失败。临时错误使用有限退避；超过上限保留为可见的死信/失败状态，不能静默丢弃。

## 10. 共享配置导出/导入

导出文件包含：

- Base token 的受控引用和显示名称；
- 选中的子表 ID/名称；
- 显示/启用状态（导入到新电脑时默认降级为草稿）；
- 字段 ID/名称、可开始值和执行/上传模式；
- Auto-Cut 包别名、并发组和并发数；
- 上传目标别名和路径绑定占位符；
- 配置 schema 版本。

导出文件不包含：

- 飞书 App ID、App Secret 或其他凭据；
- Auto-Cut 工作区绝对路径；
- ZIP 获取绝对路径；
- 本地/NAS 上传绝对路径和凭据；
- 运行租约、执行日志、任务历史和 ZIP 文件。

导入时先执行 dry-run 校验，报告缺失 Base、子表、字段、包别名和本机路径绑定；只有用户确认后才写入草稿。导入不会自动启用子表，避免换电脑后意外接收生产任务。

## 11. 失败处理与恢复

- 飞书事件重复：按现有 `event_id` 幂等状态处理；
- Taskboard 不可用：Bridge 持久化 `pending`/`retry_wait`，有限退避后重试；
- Auto-Cut 需要人工动作：任务进入 `blocked`，保留阻塞码和用户动作提示；
- 任务执行进程崩溃：启动时恢复过期执行租约，依据执行记录决定重试或阻塞；
- ZIP 尚未写完：保持产物等待状态，不进入验收或上传；
- 上传目标不可用：保留已完成剪辑状态，上传进入重试；
- 配置版本被替换：已创建任务使用旧快照，新任务使用新版本；
- 离开可开始值：只归档匹配的 `todo` 任务，不中止执行中、待验收或已完成任务；
- 归档事件延迟到下一轮任务之后：继续接受现有规范记录的轮次边界；未来如需严格隔离，再增加飞书记录版本或事件顺序约束。

## 12. 安全和运行边界

实现必须继续遵守根目录 `AGENTS.md`：

- Bridge 和 Taskboard 只监听 `127.0.0.1`；
- 飞书单元格不能提供路径、命令、shell 或 prompt；
- 包别名只能映射到本机白名单中的绝对工作区和固定 prompt；
- 状态文件使用现有稳定普通文件、互斥锁和原子替换；
- 日志和 HTTP 错误不暴露凭据、绝对路径或原始外部错误；
- 任何改变事件筛选、任务路由、凭据处理、端口、启动方式或自动 Codex 执行行为的变更，都必须同步更新测试和 README，并先在测试表/示例项目验证。

## 13. 测试与验收标准

### 13.1 配置中心

- 粘贴合法 Base 链接可以预览 Base 和子表元数据；
- 选择子表后只保存选中的显示项；
- 草稿不接收事件；
- 启用前校验字段、包别名、并发和路径；
- 不同 Base 的同名子表不会互相匹配；
- 刷新名称不会改变 `baseToken + tableId` 身份；
- 导入共享配置默认是草稿且不包含本机路径和凭据。

### 13.2 Bridge 事件

- 其他值进入配置可开始值只创建一条任务；
- 同一 `event_id` 重放不创建第二条任务；
- 离开可开始值只归档匹配的 `todo` 任务；
- 已进入 `in_progress`、`in_review`、`done` 或 `blocked` 的任务不被自动归档；
- 未知/缺失包别名创建阻塞结果，不执行本地命令；
- Taskboard 暂不可用时进入现有重试和死信机制。

### 13.3 执行和验收

- 手动点击、拖入 `in_progress` 和自动模式请求最终只产生一个执行 claim；
- 超过并发上限的任务进入队列，资源释放后继续执行；
- 同一任务重复触发不启动第二个 Auto-Cut；
- 手动模式成功后进入 `in_review`，通过验收才进入 `done`；
- 自动模式成功后直接进入 `done`；
- 授权/素材阻塞不会被标记为完成；
- 缺 ZIP 或 ZIP 校验失败不会标记剪辑完成。

### 13.4 ZIP 和上传

- 手动选择 ZIP 能计算并保存 SHA-256；
- 损坏 ZIP、目录穿越 ZIP 和不符合包结构的 ZIP 被拒绝；
- 同一 ZIP 重复入队不会产生重复目标文件；
- 目标同名不同哈希时进入冲突而不是覆盖；
- 本地路径和 UNC/NAS 路径失败后按有限退避重试；
- 上传失败不会回退剪辑状态；
- 上传成功后在已完成窗口显示目标和哈希。

### 13.5 手工端到端验收

1. 使用测试 Base 链接导入并选择一个学科子表；
2. 保存草稿，确认模拟事件不会创建任务；
3. 启用子表，模拟记录从其他值进入配置可开始值；
4. 确认创建一条待处理任务；
5. 分别验证点击启动和拖入处理中只启动一次；
6. 使用无害 Auto-Cut 包生成测试草稿和 ZIP；
7. 手动模式确认进入待验收，验收后进入已完成剪辑；
8. 手动选择 ZIP 并验证 SHA-256；
9. 加入上传队列，验证本地测试目录中的临时文件、校验和正式文件；
10. 重放事件、重试上传并重启服务，确认没有重复任务或静默丢失。

## 14. 分阶段交付

### 阶段一：配置目录和活动白名单

实现 Base 链接元数据预览、Base/学科树、字段和可开始值配置、草稿/启用、活动配置同步和共享配置导入/导出。此阶段不自动启动 Codex。

### 阶段二：统一手动执行和人工验收

实现手动点击与拖入 `in_progress` 的统一执行入口、执行 claim、并发队列、Auto-Cut 结果标准化、手动模式 `in_review` 和自动模式完成策略。根据规范变更评审决定是否开启自动模式。

### 阶段三：ZIP 产物管理

实现手动选择 ZIP、SHA-256、结构校验、产物绑定、已完成窗口和产物异常恢复。

### 阶段四：上传 Worker

实现上传队列、路径绑定、临时文件、校验、幂等、失败重试、本地和 UNC/NAS 文件系统适配。

### 阶段五：自动获取与动态路由

实现按目录自动发现 ZIP、学科代码到分支映射、总包内部路由和更细粒度的资源组策略。

## 15. 非目标

- 不把飞书字段状态通用映射成所有 Taskboard 列；
- 不由飞书单元格控制路径、命令、prompt 或凭据；
- 不在第一期改写真实飞书记录；
- 不把不同 Base 或独立学科表合并成一张业务表；
- 不把人工验收强加给自动模式；
- 不要求用户额外生成 `.sha256` 文件；
- 不删除或覆盖原始剪映草稿和用户选择的 ZIP；
- 不宣称跨外部系统副作用的绝对 exactly-once；
- 不在未通过规范、测试和 README 评审前启用自动 Codex 执行。
