# 飞书三阶段音频来源与 Auto-Cut Lite 接口交付设计

日期：2026-09-10

状态：已确认，待书面设计复核

## 1. 目标与范围

本次变更同时完成两个相互独立但契约一致的交付物：

1. 在 `codex-feishu` 的 Taskboard 面板中，把初稿、初审修改、终审修改三个阶段的“声音方式”统一改为“音频来源”，支持视频原音、文档目录和 Base 字段附件。
2. 在当前仓库维护一份可直接交给 Auto-Cut Lite 源码团队的完整 Markdown 接口需求文档，既描述当前稳定契约，也标出本次需要由 Auto-Cut Lite 新版本实现的变化。

本次不修改、不构建、不部署本机 `D:\codex\Auto-cut-lite`。该目录仅可用于只读核对现行实现和兼容基线。Auto-Cut Lite 源码团队完成新版本后，兼容验证和本机部署是后续独立动作，只有用户明确要求时才执行。

状态字段下拉选项不在本次范围内。已核实当前“高中历史”表共有 37 个字段，其中只有 4 个单选字段；状态字段下拉只显示这 4 个单选字段是预期行为，不再修改。

## 2. 已确认的产品行为

### 2.1 三阶段一致、配置独立

固定阶段仍为：

- `initial`：初稿；
- `first_review`：初审修改；
- `final_review`：终审修改。

三个阶段展示相同的音频来源控件和规则，但各自保存独立配置。修改一个阶段不得联动覆盖其他阶段。

### 2.2 音频来源控件

移除当前“使用视频原音”和“外部音频替换原音”两个分段按钮，把字段标题改为“音频来源”，并改用单选下拉菜单。选项顺序固定为：

1. 视频原音；
2. 文档目录；
3. Base 字段附件。

下拉菜单后只保留一个公用来源详情控件和一个公用“时长误差（秒）”输入框，不同时展示两套详情控件：

| 音频来源 | 公用来源详情控件 | 时长误差 |
| --- | --- | --- |
| 视频原音 | 显示但置灰，不可输入 | 显示但置灰，不可输入 |
| 文档目录 | 文本框，标题为“音频目录标题”，支持手动输入 | 可输入 |
| Base 字段附件 | 下拉框，标题为“音频附件字段” | 可输入 |

文档目录与 Base 字段附件都表示外部音频替换视频原音。时长误差是两种外部音频来源共用的正数配置，默认值保持 3 秒，最小输入和步长保持 0.1 秒。

### 2.3 Base 附件字段筛选

“音频附件字段”只显示当前 Base、当前学科表元数据中类型为附件的字段，不显示文本、数字、单选或其他类型字段。

如果当前表没有附件字段：

- 音频来源下拉中的 `Base 字段附件（无可用字段）` 置灰，不允许新选择；
- 不凭空显示或创建附件字段；
- 已有配置在元数据刷新后失去对应字段时必须显示明确校验错误，保存或启用时 fail-closed；
- 服务端在有元数据可校验时同时验证字段存在且类型为附件，不能只依赖浏览器过滤。

### 2.4 编辑期间的值保留

同一次未保存编辑中，用户在三种音频来源之间切换时，应保留刚才为各来源填写的临时值：

- 文档目录保留其目录标题；
- Base 字段附件保留其字段选择；
- 两种外部来源共用并保留同一个时长误差值。

保存时只持久化当前选中来源对应的配置。临时值不得进入共享配置、运行 manifest 或其他阶段，也不得在切换学科后串入另一学科。前端临时缓存以 `subjectKey + stageId` 为边界；重新载入已保存配置时从持久化值初始化。

## 3. 数据模型与兼容性

### 3.1 沿用现有持久化模型

本次不新增第三种 wire-level 音频 mode，也不升级 `source-manifest.json` schema。界面三种选项映射到现有模型：

```text
视频原音
  -> { mode: "video_original" }

文档目录
  -> {
       mode: "replace_original",
       source: { kind: "docx_section", anchorText: "..." },
       durationToleranceSeconds: 3
     }

Base 字段附件
  -> {
       mode: "replace_original",
       source: { kind: "base_attachment", fieldId: "..." },
       durationToleranceSeconds: 3
     }
```

生成 `source-manifest.json` 时继续转换为 snake_case：

```json
{
  "audio": {
    "mode": "replace_original",
    "duration_tolerance_seconds": 3,
    "source": {
      "kind": "docx_section",
      "anchor_text": "二、PPT草稿+翻录"
    }
  }
}
```

现有配置的兼容规则：

- `video_original` 继续显示为“视频原音”；
- `replace_original + base_attachment` 继续显示为“Base 字段附件”；
- 已存在的 `replace_original + docx_section` 显示为“文档目录”；
- 未知 mode、未知 source kind、缺少当前来源必需值或非正数时长误差继续拒绝，不做猜测迁移。

`sources.video`、`sources.review` 和其他运行契约保持不变。剪辑意见来源仍只支持文档目录。

### 3.2 各层职责

前端负责来源选择、动态标签、禁用状态、附件字段过滤和编辑期临时值保留。

Taskboard 服务端负责标准化、类型校验、当前来源必填校验、生成不可变 manifest，并继续拒绝未知字段、路径、命令、 prompt 和凭据。

Auto-Cut Lite 负责按照 manifest 获取受控来源、校验音视频时长、执行替换、生成结果、receipt 和精确 ZIP。Taskboard 不把飞书单元格内容解释为本机路径或命令。

## 4. 飞书文档目录编号兼容

### 4.1 已确认根因

飞书自动编号属于标题样式元数据，不一定属于标题正文。实际文档节点可能是：

```xml
<h2 seq="auto" seq-level="auto" seq-marker="2.">PPT定稿+翻录</h2>
```

界面显示编号，但 Auto-Cut Lite 当前只保留正文 `PPT定稿+翻录`，再与配置中的 `二、PPT定稿+翻录` 做完整字符串精确比较，因此返回 `docx_anchor_missing`。

### 4.2 Auto-Cut Lite 待实现规则

目录匹配采用“精确优先，受控编号兼容回退”：

1. 先以用户原始输入与标题正文做现有精确匹配；唯一命中时立即使用。
2. 精确匹配没有命中时，只移除配置文本和标题正文开头的一个常见编号，再对剩余正文做完整相等比较。
3. 支持的编号形式至少包括中文数字加顿号、阿拉伯数字加点、中文或英文括号编号以及分级数字，例如 `二、`、`2.`、`（二）`、`(2)`、`3.1`。
4. 兼容只作用于开头一个编号，不做子串、包含、拼音、编辑距离或其他模糊匹配。
5. `PPT草稿+翻录` 不能匹配 `PPT定稿+翻录`。
6. 多个标题去编号后等价时继续返回目录不唯一错误，不自行选择。
7. 同一规则用于三个阶段的所有 `docx_section`：视频来源、剪辑意见来源和文档目录音频来源。
8. 同一规则也用于章节结束边界判断，避免内容跨入下一章节。
9. 配置和 manifest 始终保留用户原始输入，不在 Taskboard 中静默删除或改写编号。

该算法属于 Auto-Cut Lite 源码端变更，本次只写入接口需求文档，不直接修改当前电脑中的 Auto-Cut Lite。

## 5. Auto-Cut Lite 统一接口文档

### 5.1 文件与定位

实现完成时在当前仓库新增并持续维护：

```text
taskboard/docs/auto-cut-lite-interface-requirements.md
```

这是 Taskboard 与 Auto-Cut Lite 之间的唯一可转交接口需求文档，不直接复制历史设计稿。用户以后要求“Auto-Cut 接口文件”时，应先按当前代码、测试和新增需求重新核对并更新同一文件，再提供给用户。

### 5.2 文档结构

文档至少包含：

1. 文档版本、生成日期、Taskboard 提交基线、已核对的 Auto-Cut Lite 兼容基线和状态说明；
2. 当前稳定契约；
3. 本次 Auto-Cut Lite 源码端待实现变更；
4. 完整验收测试；
5. 兼容性和发布要求；
6. 变更记录。

每条行为使用明确状态标识，至少区分：

- `CURRENT`：当前双方已支持，升级不能破坏；
- `REQUIRED`：本次源码版本必须新增或修改；
- `OUT OF SCOPE`：明确不由本次实现。

### 5.3 必须覆盖的完整契约

文档不是仅描述本次增量，而要覆盖源码团队实现和自测所需的全部现行边界：

- 安装发现和 `deployment-report.json` 校验；
- `review-document-run` 固定命令行参数；
- 全部 `CODEX_AUTOCUT_*` 环境变量及继承环境清理规则；
- `source-manifest.json` schema v1、规范化 JSON 和 SHA-256；
- `execution_input.json` schema v1 和安全文件名规则；
- 三阶段 binding、飞书记录身份、Docx/Wiki URL 和来源类型；
- 视频原音、文档目录音频、Base 附件音频及正数时长误差；
- Auto-Cut 自身用户身份、飞书访问授权、路径和凭据隔离；
- `result.json` 成功与阻塞结构；
- 相邻 `receipt.json` schema、binding、hash、草稿名和 source pair 约束；
- `taskctl artifact report` 的 loopback URL、Bearer token、请求体和退出码；
- 精确 ZIP 路径、文件名、hash、草稿根和 `driver_report` 一致性；
- ZIP 大小、格式、CRC、目录穿越、重复条目和草稿 JSON 校验；
- 稳定错误码、阻塞语义、状态转换和 fail-closed 行为；
- 本次文档目录自动编号兼容要求；
- 源码团队可以直接执行的正常、边界、歧义和失败验收用例。

文档中的 JSON 示例和命令必须完整可复制；秘密值、真实 token、真实绝对业务路径和运行状态不得写入文档。

## 6. 方案比较与决策

曾考虑三种交付形式：

1. 单一长期完整契约文档，并在其中区分当前基线与待实现变更；
2. 一份基线文档加每次独立的增量需求文档；
3. 每次只交付本次差异说明。

采用方案 1。它符合用户“拿到一个文件即可直接交给 Auto-Cut Lite 源码团队”的使用方式，也能通过状态标识和变更记录避免混淆当前能力与目标能力。方案 2 需要接收方同时维护多份文件；方案 3 容易遗漏既有安全和产物契约，均不采用。

## 7. 错误处理与安全边界

- 三个阶段任何一个已启用阶段配置不合法时，保存或启用必须给出对应阶段的明确错误，不能生成半有效运行配置。
- 选中外部音频但目录标题为空、附件字段为空或字段类型不符时 fail-closed。
- 视频原音不要求外部来源和时长误差，运行 manifest 只输出 `mode`。
- Auto-Cut Lite 无法唯一找到目录、找不到附件、时长超差、结果或 receipt 不一致时必须返回稳定阻塞码，不得退回其他来源继续执行。
- Bridge、Taskboard 继续只监听 `127.0.0.1`；本次不改变事件筛选、自动执行资格、包白名单或凭据处理。
- 飞书单元格只能提供受控字段值和附件引用，不能提供工作区路径、shell、Codex 参数或 prompt。
- 模拟事件继续不得获得自动执行资格。
- 当前 Auto-Cut Lite 目录及已部署运行时不得被本次任务修改。

## 8. 测试与验收

### 8.1 Taskboard 自动化测试

实施应先补失败测试，再修改实现，覆盖：

- 三个阶段都渲染同一套“音频来源”下拉及公用控件；
- 视频原音时详情和时长误差可见但置灰；
- 文档目录时详情切换为可输入的“音频目录标题”；
- Base 字段附件时详情切换为“音频附件字段”下拉；
- 下拉只包含附件字段；无附件字段时来源选项置灰并显示说明；
- 三种来源切换时保留本阶段本学科的临时值，不跨阶段或学科泄漏；
- 保存后只保留当前来源；旧配置能正确回显；
- 服务端接受文档目录音频并生成正确 manifest；
- 服务端拒绝空标题、缺失字段、非附件字段、未知 mode/kind 和无效时长；
- 初稿、初审修改、终审修改分别生成自己的来源配置；
- 共享配置导入导出保持兼容且不携带临时编辑缓存。

按仓库规范至少运行根目录 `npm test`。界面改动还要启动本地服务，使用桌面和窄屏视口检查三个阶段的控件布局、禁用状态、文本截断和切换交互。

### 8.2 Auto-Cut Lite 源码团队验收

统一接口文档必须给出可执行测试矩阵，至少验证：

- 视频原音保持现有行为；
- 文档目录音频被提取并替换原音；
- Base 附件音频被下载并替换原音；
- 三种来源在三个阶段都可运行；
- 时长在误差内通过，超差稳定阻塞；
- 手工正文编号、飞书自动编号、无编号和分级编号均按“精确优先、编号回退”匹配；
- 去编号后正文不同不匹配；
- 去编号后多个候选返回歧义；
- 视频、意见、音频的章节边界不串段；
- 所有 result、receipt、report 和 ZIP 校验保持现行契约；
- 任一身份、路径、hash 或 schema 不一致均 fail-closed。

### 8.3 发布顺序

1. 在 `codex-feishu` 当前功能分支完成 Taskboard 改造、测试、README 和统一接口文档；
2. 代码评审后把接口文档交给 Auto-Cut Lite 源码团队；
3. 源码团队在其源码仓库实现并构建新版本，不修改当前电脑的已部署副本；
4. 取得候选版本后，按统一接口文档在测试表和示例项目验证；
5. 用户明确要求后才在当前电脑部署；
6. 部署后再做真实飞书事件端到端验证。

## 9. 完成标准

只有同时满足以下条件，当前 `codex-feishu` 工作才算完成：

- 三个阶段的音频来源交互和配置均符合本设计；

- 自动化测试、界面验证和 README 更新完成；
- `taskboard/docs/auto-cut-lite-interface-requirements.md` 已包含完整现行契约、本次待实现需求和验收矩阵；
- 工作区没有修改 `D:\codex\Auto-cut-lite` 或部署目录；
- 相关变更经过代码评审。
